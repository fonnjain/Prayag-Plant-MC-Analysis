# Prayag Production Analytics

A mobile-first Flask dashboard that reads Prayag's real production Google Sheets (by explicit file ID) and computes OEE / utilisation / efficiency / rejection metrics deterministically — Claude only writes narrative prose from already-computed numbers.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required env: `DATABASE_URL` — Postgres connection string

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Where things live

- `artifacts/prayag/confirm.py` — deterministic four-tier Data Confirmation engine. `build_masters` (roster of machines/segments/moulds/units per plant from full-FY grid), `expected_files_for`, `tier1_completeness`/`tier2_reconciliation`/`tier3_validity`/`tier4_plausibility`, `full_confirm(...)` → {status, score, score_label, issues, tiers, counts, reconciled, summary}. Tier1 checks files/machines/months score plus segment & mould roster coverage (missing-from-data and unknown-in-data, both ways). Tier2 reconciles each sheet's stored TOTAL vs detail, the engine self-reconcile, AND hierarchy (segment == Σ its lines: flags a machine split across segments, a segment total ≠ Σ lines, and output with no segment assigned). Pure; no network. Caller may pass an optional `matcher` (Claude) used only to fuzzy-map leftover machine codes.
- `artifacts/prayag/sources.py` — real Google Sheet file IDs (`ANNUAL_SOURCES`, `DAILY_SOURCES`), `PLANT_NAMES`, `FY_MONTHS` (current FY2026-27) + `FY_MONTHS_2526` (prior FY2025-26, selectable as the `prior_fy` period). `DAILY_SOURCES["PIPE"]` holds BOTH FY years; each Pipe & Fitting workbook feeds PIPE (Report-5↔Report-11) AND MOULDING (Report-12). `EMPTY_SOURCES` = `{(plant, "YYYY-MM")}` of wired-but-empty template workbooks (e.g. PIPE 2025-08): the loader (`_load_daily`) short-circuits these to a no-record "empty / awaiting source" report instead of reading them as a real zero-output month. Source of truth for what gets read.
- `artifacts/prayag/sheets.py` — Drive/Sheets readers + caching. Monthly grid (`get_records`) and daily matrix (`get_daily_records`, `_load_daily`). `detected_sources()` lists everything wired up.
- `artifacts/prayag/parsers.py` — deterministic layout parsers: `parse_mc_detail`/`grid_total_output` (monthly), `parse_daily_matrix` (wide per-date matrix).
- `artifacts/prayag/metrics.py` — `Record` (grain-agnostic), `compute_metrics` (recomputes every ratio), `rollup_by_*`.
- `artifacts/prayag/store.py` — durable manager review store (Replit Postgres via psycopg2, append-only). Two tables: (1) `confirmation_signoffs` for period-level sign-offs — `record`/`effective`/`history`, keyed to (unfiltered period_key, confirmation fingerprint), latest `approve`/`revoke` wins; (2) `confirmation_issue_acks` for per-issue acknowledgements — `ack_record`/`acks_for`, keyed to (unfiltered period_key, stable `confirm.issue_key`), latest `ack`/`unack` wins. Both degrade to a safe no-op (gate stays ON / no acks) when `DATABASE_URL` is absent. A third table `source_fingerprints` (file_id, fingerprint, label, plant, grain, row_count, observed_at) backs the spreadsheet-change tracking — `fingerprint_state()` (latest snapshot per file + distinct-version count) and `fingerprint_record(...)` (best-effort, returns None on failure). One row per content version: a UNIQUE index on (file_id, fingerprint) + `INSERT … ON CONFLICT (file_id, fingerprint) DO UPDATE SET observed_at = now() … RETURNING *` means concurrent duplicate inserts collapse to one row AND a revert to a previously-seen version re-stamps it as the latest so the panel converges (never a perpetual "changed"). Degrades to no-op without `DATABASE_URL`.
- `artifacts/prayag/verify.py` — deterministic, network-free **read-only** Data Verification assembly. `build_verification(month, monthly_rows, monthly_reports, daily_rows, daily_reports, tol=0.005)` → per plant→machine→month figures with provenance (`source_file_id`/`source_sheet`/`source_ref`/`ideal_source`), plant + grand roll-ups, and three checks (daily-vs-summary, row-vs-total, plant-vs-machines) each PASS/FAIL/NA at 0.5% tol; `rows_to_csv`/`CSV_HEADER` for export. Mirrors the `_mc_key` machine-number join; PIPE daily output is now gross (Report-5 Col G), so it no longer carries the old Report-11 net-of-rejection skew. `source_ref` is the machine's own row label, not a fabricated A1 cell.
- `artifacts/prayag/freshness.py` — deterministic, network-free **spreadsheet-change tracking** (dashboard-detected "last updated / what changed"). `compute_fingerprints(records)` sha256-hashes each source workbook's parsed sheet-sourced fields (`_FP_FIELDS`, excludes the derived `ideal_hours`) over sorted canonical lines so it is order- and int/float-jitter-independent (the connection can't read Google's true `modifiedTime`, so this content hash IS the change signal). `build(records, now=)` reconciles against `store.fingerprint_state()`, records a snapshot only on a genuine transition (first sight, or current ≠ last-seen version — never on an unchanged re-read), and returns a template-ready dict {available, recent_days (7), checked_at_disp, sources[], n_total, n_updated, updated[]}; first sight = baseline (not flagged), a change within `RECENT_DAYS` = "updated". It also lists configured-but-never-observed workbooks as "Not yet observed" so the panel is a complete inventory of all sources. Degrades to a listing-only no-op without `DATABASE_URL`.
- `artifacts/prayag/app.py` — Flask routes; `parse_period` (period→months + `sub_monthly`; the **default** period `last_updated` searches the last 60 days and `get_data` narrows it to EACH plant's OWN most recent date with real daily data — a per-plant "freshest snapshot" (so a plant reporting less often, e.g. Moulding/HDPE, still appears with its own last-updated date instead of vanishing when another plant reported more recently) that skips empty in-progress days; the grain banner lists every shown plant + its date, and plants with no recent daily data simply don't appear), `get_data` (grain-aware daily-vs-monthly resolution; also stamps `confirmation` with `period_key`/`fingerprint`/`signoff`/`released`, plus `freshness` — per-plant latest reporting date from daily rows only, shown in the completeness panel as "Data reported through: …", computed AFTER `full_confirm` so the pure engine is untouched). `/confirmation/approve` + `/confirmation/revoke` (POST) record period sign-offs against the live data state; `/confirmation/ack_issue` + `/confirmation/unack_issue` (POST) record per-issue acknowledgements. `get_data` loads effective acks, marks each issue `acknowledged`, and downgrades status error→warning when every blocking error is acknowledged. Verification routes: `GET /verify` (`?month=`/`?period=YYYY-MM`, defaults to latest data month; degrades to monthly-only on daily `SheetReadError`), `GET /verify.csv` (provenance export), `POST /verify/log` (append-only audit entry — writes NO fact data).
- `artifacts/prayag/templates/*.html` — grain-aware UI.

## Architecture decisions

- Daily-first headline figures: monthly AND FY views compute plant/machine/segment totals by summing the authoritative daily files (one tab per metric), not the monthly summary grid. The grid undercounts (e.g. PIPE May grid ≈81,654 vs daily 107,609), so it is kept only as a reconciliation reference — surfaced as a NON-BLOCKING note (`get_daily_records` already emits the daily-vs-grid gap) and never used to reduce the daily figures. The grid is the headline only for a month with no daily workbook at all; under the daily-only rule a TOTAL daily-read outage on a monthly/FY view shows NO production data with an honest error banner — the lower grid total is never substituted in. `get_data` runs the daily-first path for every period and refuses any grid substitution (both sub-monthly windows and monthly/FY outages). `get_daily_records` isolates per-(plant, month) read failures (a single transient 429 on a cold FY read no longer nukes the whole period) and raises only when every workbook fails.
- All ratios are recomputed in Python from raw cells; stored % cells are never trusted. Claude only writes prose from already-computed numbers.
- Daily data is ingested for EVERY plant with a daily workbook, via a per-plant layout config (`_DAILY_LAYOUTS` in `sheets.py`): `long` (row-per-machine-per-date: PIPE, MOULDING), `matrix` (wide per-date grid: PTMT, HDPE), `blocks` (one per-machine block tab: GARDEN), `tank` (per-item PROD. REPORT: TANK). The ideal denominator (for utilisation/efficiency) degrades by precedence — manager OVERRIDE (app DB, `/input` page, see below) → in-sheet ideal-OUTPUT rate (a plant publishing its own per-machine Ideal Output, e.g. HDPE) → in-sheet ideal-HOURS column (PTMT) → PIPE/MOULDING's cross-tab derived ideal (Report-5 "Ideal Run Hour Per Day" × the machine's run days) → config baseline (baselines.json) → app-logic default (`ideal_hours.APP_DEFAULT_IDEAL_HOURS`) → none. The monthly grid's "Ideal Hours" is a flat placeholder (500 for every machine), NOT a real planned-hours baseline, so it is deliberately NOT a precedence step. The app-logic default tier carries real planned hours that are NOT published in the sheets (GARDEN=500, TANK=500, HDPE=550 hrs/machine/month, `ideal_source="app_default"`, badge "App default"); it is the lowest tier, applied in `sheets._emit_daily` only when no higher tier matched. CAVEAT: TANK records OUTPUT only (its daily parser sets `actual_hours=0`), so the default supplies the utilisation DENOMINATOR but utilisation stays SUPPRESSED (never a fake 0%) — enforced by `ideal_hours.PLANTS_WITHOUT_RUNHOURS={"TANK"}` → `Record.runhours_tracked=False` and a SEPARATE `util_ideal` denominator in `compute_metrics` that excludes untracked rows (so the default also never dilutes a mixed rollup's utilisation; `m.ideal_hours` still includes it as the honest planned-hours total). GARDEN reads OUTPUT from its per-machine block tabs (MACHINE 1–4) but ALSO joins per-machine per-date RUN HOURS from the workbook's "Daily Report" matrix tab (`runhours_tab` in `_emit_blocks`, joined by machine number + date; output is NEVER taken from the matrix), so its utilisation now computes against the app-default 500 hrs/machine/month. The 500 is spread ONLY across the days a machine actually logged run hours: the monthly rollup still uses the full 500 per machine, AND a day with output but no run hours keeps `ideal_hours=0` → utilisation BLANK (no fake 0% at the day grain either); a machine/month with no run hours at all (matrix not yet filled, e.g. an in-progress month) stays fully suppressed. HDPE logs run hours, so its utilisation computes against 550 once its (currently empty) workbooks are filled. PIPE and MOULDING both derive a real per-machine utilisation baseline from the Pipe&Fitting workbook's Report-5 (Ideal Run Hour/Day × the machine's Total Run DAYS, `ideal_source="derived"`, distributed across each machine's daily rows so a full-month rollup reconciles). EFFICIENCY (output-efficiency) is then (output ÷ run hours) ÷ Report-5 Col I "Ideal Output Per Hour" (per machine, never global): PIPE lines publish Col I so efficiency computes; MOULDING rows leave Col I blank so efficiency stays n/a (the spec's IFERROR rule — never a fake 0%). No clamp: a machine past its ideal output legitimately reads >100%. The missing-baseline flag is an advisory, non-blocking warning — it never gates sign-off. baselines.json ships with NO machine entries; only real, business-supplied planned hours may be added (never estimates or the 500-h placeholder). Plants without any baseline still show raw hours + output; utilisation/efficiency are suppressed (not a misleading 0%) with a "No baseline set" notice. HDPE reads its 6 machines (M/C-1…6) from the "Daily Report" matrix tab (the separate DANA support tab is never read) and supplies its own in-sheet Ideal Output (kg/hr → efficiency) plus M/C Run Hour (monthly available hrs → utilisation), so it needs no baselines.json entry. HDPE still HAS a monthly grid (it is in `ANNUAL_SOURCES`), so its completeness roster comes from that grid like the other gridded plants — it is NOT given a fixed injected roster. TANK has no machine identity, so its roster is the daily-reporting items themselves (dynamic, plant-level). PTMT also has no monthly grid, but its roster is the authoritative 55-machine register in `sources.PTMT_GROUPS` (5 process groups) — so completeness is held to all 55 (a never-reporting machine is a gap, not silently dropped) and each machine's process group + finishing flag come from that file, with `_ptmt_group`'s string heuristic kept only as a fallback for unknown codes.
- `_mc_key` joins daily↔monthly machines on M/C-n or MACHINE-n only (ignores SOCKET/Grinder/die codes) to prevent mis-joins.
- Report-5-only auxiliary machines (grinders, pulverizers, sockets, mixers in the Pipe&Fitting workbook) have NO daily tab, so they would otherwise never produce a record. `sheets._emit_daily` synthesises one MONTH-grain Record per such machine (after the daily precedence loop, gated by `_r5_aux_class` which recognises ONLY grind/pulver/socket/mixer — everything else returns None so real pipe/moulding lines and idle M/C-n rows never leak in as bogus auxiliaries). Owner plant comes from the label's `(PIPE)`/`(MOULD)` tag (untagged sockets/mixers → PIPE); skipped if already matched to a daily machine (by `_mc_key` or `_r5_norm`). Each carries run-day utilisation = run hours / (ideal-per-day × run days) with `ideal_source="derived"` and NO clamp (a grinder legitimately exceeds 100%). Idle rows (0 run days) get ideal_hours=0 so utilisation/efficiency stay BLANK (never a fake 0%). All are `is_finishing=True` (own segment `"{PLANT} – Grinding/Pulverizing/Socketing/Mixing"`, output excluded from the plant headline). Efficiency uses the sheet's Ideal Output Per Hour (Report-5 Col I); a blank Col I (e.g. Grinder-3, in-sheet #DIV/0!) → efficiency n/a plus a non-blocking advisory note (surfaced via `report["notes"]` → `get_daily_records` warnings). These month-grain records are EXCLUDED from sub-monthly day windows and from the per-plant freshness / `last_updated` computation in `app.get_data` (guarded on `r.grain == "daily"`), since a whole-month figure cannot be sliced into a day.
- Per-day ideal hours = monthly ideal hours ÷ the machine's active days that month, so a full-month daily rollup reconciles exactly to the monthly grid (verified: 831 actual / 5000 ideal hrs both paths).
- In `compute_metrics`, daily rows with `shift_len_min > 0` are true shift-logs (time model, feed OEE); daily-matrix rows (`shift_len_min == 0`) carry hours/output directly like monthly rows.
- For sub-monthly windows, monthly totals cannot be sliced into a partial month, so `get_data` shows only daily-capable plants and banners the omission rather than mixing in non-sliceable monthly totals.
- Data Confirmation runs four deterministic tiers on every page over the UNFILTERED period rows (a plant/machine filter never makes the dataset look incomplete). The full-FY monthly grid is the master roster; a blank in a later period is a completeness *gap*, never an implicit zero. Severity gating: validity / internal-reconcile-mismatch / no-data = error (figure shows "needs review"); completeness, sheet-reconcile-off, plausibility = warning. Claude (`match_codes`, `summarize_confirmation` in `narrative.py`) only fuzzy-matches leftover machine codes and writes prose from the already-computed issue list — it never reads or computes a figure.

## Product

Mobile-first dashboard over Prayag's real production sheets: OEE/utilisation/output-efficiency/rejection by plant, machine, segment, mould, and period. Supports FY/month views (monthly grain) and sub-monthly windows (Last Updated / Yesterday / 7d / 30d / custom) which surface true per-day data for daily-capable plants, with deterministic reconciliation against the monthly grid. "Last Updated" (the default) resolves PER PLANT to each plant's most recent day that actually has production data, so every active plant lands on real figures with its own last-updated date (shown in the grain banner and the completeness panel); a dormant plant with no recent daily data is simply not shown (never fabricated).

- Brand colours: navy `#1F3864`, terracotta `#C55A11`. Dates displayed dd-mm-yyyy.
- Read real production sheets by explicit file ID; never fabricate or silently fall back to demo numbers.

## Gotchas

- PIPE output & rejection are **reconciled** between **Report-5** (per-machine matrix: per-date Run/Output/Rejection from col O) and **Report-11** ("M/C & Item Wise Actual Production" item journal): the headline figure for each (machine, date) cell is the **date-wise MAX** of the two sources over the UNION of their cells (`pipe_reconcile.reconcile`). Neither alone is complete — Report-5 carries authoritative run hours and many machine-days, but Report-11 logs machine-days Report-5 omits (and occasionally a higher per-cell figure), so taking the max recovers the true total without ever double-counting (it is a max per cell, not a sum of both). Output and rejection maxima are picked **independently** per cell. Validated live for April 2026: Report-5 alone = 135,634; Report-11 alone = 157,278; reconciled = **157,883** output / **13,030** rejection. Both sources are parsed **header-based** (`pipe_reconcile.parse_report11` + the matrix parser locate columns by header text, e.g. the standalone "Weight" output column, "Actual Wt (Kg)" reject, "TYPES"), so the SAME readers handle BOTH the FY2025-26 and FY2026-27 sheet layouts. **Type split** (CPVC/UPVC/SWR/AGRI) comes from Report-11's TYPES column, allocated **pro-rata** to each cell's corrected output; a cell present only in Report-5 (no Report-11 type signal) becomes an **"untyped pickup"** bucket — the type split is **audit-only** (`report["pipe_reconcile"]`), never reduces the headline, and always reconciles exactly (Σ types + untyped == corrected output). Machines whose corrected output comes from Report-11-only days (no Report-5 run hours) are appended as daily rows with `actual_hours=0` and **flagged** — their efficiency is understated because output rose but logged run hours did not. Report-5 is one tab holding multiple machine families (Pipe M/C, Socket, Mixer, Grinder/Pulverizer, Moulding A01…D07); PIPE keeps only the M/C-n extruder rows (`mc_only` filter via `_mc_key`) — auxiliaries are synthesised separately (finishing) and Moulding is read from Report-12. CAVEAT: Report-5's own Pipe **TOTAL row** sums only a stale machine range (its formula was never extended when later M/C-n rows were added below it), so the daily-first sum of every M/C-n row is HIGHER than that stale TOTAL by design — the sum of real machine rows is authoritative, the sheet's TOTAL formula is not. GARDEN reconciles exactly. (Note: `verify.py`'s provenance still labels PIPE output by its Report-5 source ref; the reconciliation max happens upstream in `_emit_daily` before verification.)
- MOULDING output is measured in **kg** (read from Report-12's "Wt in Kgs" column), so its plant `unit` in `sources.ANNUAL_SOURCES` is `kg`, not `pcs`. This unit flows to records, the verify kg/pcs bucketing, and the Tier 4 plausibility check. The plausibility (Tier 4) output-outlier message embeds the row's unit (e.g. "output 147 kg is 0.0× the Moulding median (2,948 kg)") because the plausibility narrative is written by Claude from the deterministic issue text only — if the message omits the unit, Claude guesses one ("pieces"), so figure-citing tier messages must carry their unit.
- PTMT Report-5 (and similar matrices) have NO per-date rejection column — daily groups carry only Run Hours + Output, and a single monthly "Actual Rejection Weight" column sits after the 31 date groups. The matrix parser's last date-group spans to the row end, so the whole month's rejection lands on the LAST day's row (every other day reads reject=0). Summing the daily rows still recovers the correct monthly rejection, but it means a single-day view of that last day shows an inflated rejection figure. Because of this, the Tier 3 "rejects exceed output" impossibility check runs at the **machine-month aggregate** grain (sum output vs sum reject per plant·machine·month·grain), NOT per daily row — otherwise the lumped last-day reject false-flags as impossible and wrongly quarantines valid output. A genuine month-level reject>output still quarantines every row for that machine-month.
- Daily ingestion covers every plant with a daily workbook (PIPE, MOULDING, GARDEN, HDPE, PTMT, TANK). PIPE/GARDEN/MOULDING have monthly grids; PTMT/TANK do not. PTMT shows raw output plus its in-sheet ideal column without a grid cross-check; HDPE also has no grid cross-check but publishes its own in-sheet Ideal Output (kg/hr) and M/C Run Hour, so its utilisation and efficiency are computed from the daily matrix itself. TANK is logged per item with no machine identity, so it shows plant-level output + item detail and no per-machine OEE. PTMT regrind/grinder KG carries `is_finishing=True` and is excluded from the plant total to avoid double-counting (the Grinding segment still shows it when viewed alone).
- PTMT machines carry **process-group** segments (`PTMT – Injection (standard)`, `PTMT – Corrugator`, `PTMT – Grinding`, …), never a flat `PTMT` segment. So any report whose `REPORT_TYPES[*]["segments"]` lists a plant token (e.g. `injection_summary` = `["PTMT", "CP"]`) must match those groups by prefix — `report_detail`/the report-table builders go through `_filter_report_segments`, which matches the exact segment OR `segment.startswith(f"{token} ")`. A plain `r.segment in rpt["segments"]` silently shows "No data" for PTMT even though the engine computed utilisation fine. PTMT utilisation itself is wired live from Report-5 Col E (IDEAL HOUR), recomputed as run hours (Col D) ÷ ideal (Col E), never the stored Col F %; Col E is a FLAT 572 h/machine/month (does not scale with calendar days) and is read per-month from the live cell, never hardcoded. PIPE and MOULDING both derive their utilisation baseline from the Pipe&Fitting Report-5 "Ideal Run Hour Per Day" (× the machine's Total Run DAYS, `ideal_source="derived"`); PIPE efficiency uses Report-5 Col I "Ideal Output Per Hour" per machine, while MOULDING efficiency stays n/a (Col I blank for moulding rows).
- Run the app via the workflow (`PORT=21800 python3 app.py`); for ad-hoc curl use `localhost:80/...` through the shared proxy.
- Spreadsheet-change tracking (`/confirmation` + `/sources` "Spreadsheet updates" panel, shared partial `templates/_freshness_panel.html`) is fed by `app._build_freshness()`, which fingerprints the FULL current dataset (`get_records` + `get_daily_records` over `months_with_data()`) so the panel is view-independent and identical on both pages. The fingerprint MUST be cross-process deterministic (it persists across worker restarts): sort the canonical lines and normalise numerics (`_num` coerces int↔float to a fixed 4-dp form) — an int-vs-float re-read of the same cell must hash identically or every page load false-flags a change. Changing the fingerprint formula (or `_FP_FIELDS`) invalidates existing baselines, so each prior version re-appends as a spurious "changed" snapshot; after a formula change, `TRUNCATE source_fingerprints` to re-baseline cleanly (it holds no user data, only detected snapshots).
- Manager sign-off releases the ERROR gate only (warnings already publish). There is no login, so the approver name is typed into the form and recorded as-is — it is an attestation, not authenticated identity. A sign-off binds to the exact data state (fingerprint); any change to the underlying sheets re-gates the figures automatically and the prior sign-off no longer applies.

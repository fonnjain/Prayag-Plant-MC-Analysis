# Ingestion Manifest & Reconciliation Spec

**Purpose:** After the Replit app fetches current data from Google Drive, it builds a
*manifest* of what it read, runs two deterministic reconciliations, and then hands the
result to Claude for an **advisory** review (see `advisory_pass_prompt.md`).

**Division of labour (non-negotiable):**
- **Code is authoritative** for *what was fetched*, *what is missing from expected scope*,
  and *per-file invariants* (output >= reject, columns present).
- **Claude is advisory only** for the fuzzy layer: stale/partial detection, naming/code
  drift, and files that exist in the Drive but are outside the app's expected scope.
- Nothing Claude returns may auto-modify a published figure or auto-expand ingestion scope.

---

## 1. Manifest (built in code, immediately after fetch)

One `fetched` entry per file the app *tried* to read, plus a raw, unfiltered Drive listing.

### Field notes (the ones that matter, and why)

| Field | Why it exists |
|---|---|
| `date_range_in_data` + `rows_found` | Catches a file that is **present but stale or partially filled** — the case a pure file-exists check misses. |
| `columns_seen` | Lets a schema check confirm the right columns are present *before* any number is trusted. **This is the layer that guards against the wrong-column class of bug; coverage alone does not.** |
| `aggregates.output_ge_reject` | Cheap deterministic invariant per file, re-asserting validity at ingest rather than only deep in the pipeline. |
| `drive_actual` | Raw, **unfiltered** listing of every spreadsheet under `root_folder_ids`. Do NOT filter it against `expected_universe` — that filtering is the whole point of reconciliation #2. |

> Make `root_folder_ids` as broad as reasonable (top-level parent, not per-plant subfolders).
> `drive_actual` can only surface files in folders the listing actually traverses.

## 2. Deterministic reconciliations (in code, before calling Claude)

The app computes both itself and includes the verdicts in the prompt, so Claude reviews a
finding rather than inventing one.

### 2a. Expected - Fetched  (did we get everything we expected?)

```json
{
  "coverage": {
    "expected_count": 18,
    "fetched_with_data": 11,
    "present_but_empty": [
      {"plant": "HDPE",  "month": "2026-04"},
      {"plant": "HDPE",  "month": "2026-06"},
      {"plant": "Tanks", "month": "2026-04"},
      {"plant": "Tanks", "month": "2026-05"}
    ],
    "not_found_at_all": [],
    "stale_suspects": [
      {"plant": "Pipe & Fitting", "month": "2026-06",
       "data_through": "2026-06-04", "as_of": "2026-06-14"}
    ]
  },
  "schema_flags": [
    {"plant": "Injection Moulding",
     "issue": "daily codes don't map to roster (24 reporting)"}
  ]
}
```

### 2b. Drive_actual - Expected  (did the Drive contain something we never expected?)

```json
{
  "unaccounted_raw": [
    {"file_id": "1ab...", "title": "4. EPS Date Sheet & Monthly Report - May ' 2026",
     "parent": "EPS_folder_id"}
  ]
}
```

`unaccounted_raw` is a naive set-difference and **will contain junk** (templates, archives,
duplicates). Deciding which entries are real plants the pipeline should ingest is the fuzzy
job handed to Claude — see reconciliation review in the prompt spec.

## 3. Schema check spec for `columns_seen` (guards the wrong-column bug)

Run in code per `fetched` entry, before trusting aggregates:

- **Required-column presence:** each plant has a known set of expected headers
  (e.g. PTMT Report-5 must contain `TOTAL` and `Actual Rejection Weight (in Kgs)`).
  Missing a required header => `schema_flag` of type `missing_column`; do NOT compute
  validity/efficiency for that file.
- **Unit/column-identity guard:** the column used as "output" must be the agreed one
  per plant (PTMT = gross `TOTAL`; Injection Moulding = net `Wt in Kgs`). Record which
  column was used in `aggregates` so a reviewer can confirm.
- **Invariant:** `output_kg >= reject_kg` at file level. If violated, flag — but flag it as
  *"investigate column mapping first"*, since the historical failure here was a read error,
  not real data.

> Coverage answers *"which sheets were updated."* The schema check answers *"are we reading
> the right cells in them."* You need both; the second is what actually bit this pipeline.

---

## 4. Run-logging (so you can tell WHERE a miss happened)

Persist, per run: the full manifest, both reconciliations, and Claude's response.
When something slips through, this lets you tell apart:
- a gap in the **manifest** (app never captured it), vs
- a gap in the **review** (Claude missed/misjudged it).
They have different fixes.

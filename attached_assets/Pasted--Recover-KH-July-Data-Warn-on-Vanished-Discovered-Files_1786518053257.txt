## PHASE 2 — Warn when a previously-discovered file becomes unreadable

Today a discovered file vanished from Drive and KH July silently became "no data": discovery no longer finds it → `_load_daily` gets `file_id = None` → `return []` → the month renders empty with **no error, no flag, no note**. A month of production disappearing silently is exactly the failure this codebase exists to prevent.

**Add a non-silent path. Do not change discovery's behaviour or any parsing logic.**

1. Keep a small persistent record of `(plant, ym) → file_id` for months that discovery has previously resolved (a `sheet_cache` key such as `discovery_seen` is fine — do not create a new table, and do not touch existing daily keys).
2. When `ensure_daily_discovery` runs and a `(plant, ym)` that was previously seen is **no longer found in the folder scan**, or its file ID now errors (404/403) on read, emit a warning that surfaces in the same place other source warnings appear (the report dict `warning` field / data-health panel):
   > `TANK 2026-07: a previously discovered source file is no longer readable (was 10_CbcKzvWd…). This month may show no data. Source may have been deleted, moved, or had access revoked.`
3. **Distinguish three states** and do not conflate them:
   - never had a file → existing "awaiting source" behaviour, unchanged
   - has a file, genuinely zero production → existing known-empty behaviour, unchanged
   - **had a file, now unreadable → the NEW warning**
4. Do not auto-remove the discovered entry, do not fall back to another month, and do not fabricate a figure. The month still shows no data — it just says why.

**Validate:** the warning fires for `TANK 2026-07`; no warning for months that never had a file; no warning for genuinely-empty months (e.g. KH April, whose registered workbook has zero rows); no change to any figure anywhere; discovery still picks up new months normally (August entries unaffected).

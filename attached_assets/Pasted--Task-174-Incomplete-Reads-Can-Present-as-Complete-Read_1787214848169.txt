## The evidence

Two reads in one session, **no cache clear between them**, same window:

| Read path | PTMT rows | Non-finishing total |
|---|---:|---:|
| via `get_data` (dashboard) | 3,968 | 400,286.78 kg |
| direct daily-source read | **5,351** | **557,264.06 kg** |

**1,383 records and ~157,000 kg apart**, with nothing marking the first as incomplete. It returned a smaller, entirely plausible figure. This is very likely what produced the historic **628,620.752 kg** PTMT reading.

**This is not PTMT-specific.** `get_data` loads every plant through the same path.

## Gap 1 (confirmed) — the guard exists, most consumers ignore it

`_failed_pairs` is produced at `sheets.py:2822` and consumed by **four** builders: Garden, HDPE, Pipe, Tank.

**It is not consumed by:**
`mgmt_moulding_summary` · `mgmt_gom_summary` · `mgmt_ptmt_summary` · `mgmt_labour_power` · `mgmt_pipe_moulds_summary` · `mgmt_ptmt_mould_eff`

**And `app.py` does not consume it at all** — so the dashboard path (plant view, machine view, overview, report detail) has no partial-read protection.

## Gap 2 (confirmed) — it only fires on an exception

`sheets.py:2797`:

```python
except SheetReadError:
    failed_pairs.append(pair)
```

A pair that returns **successfully with zero or fewer records than expected** never enters the list. That is precisely the case here: a read that neither threw nor returned everything.

**So the guard did not fire because it cannot fire on a silent partial.** That answers the question before it is asked.

## STEP 2 — Fix

**(a) Widen what counts as a failure.** A registered `(plant, ym)` that returns **zero records, or fewer than a previous successful read for the same pair**, must enter `failed_pairs` alongside the exception case. *"We could not read it"* and *"there was no production"* must never render the same way (**R-06**, **R-07**, Failure Mode #9).

Distinguish carefully: a month with a registered source and genuinely no production is legitimate — HDPE April and June are real idle months. The signal is **a source that is registered and returns nothing where it previously returned rows**.

**(b) Consume it everywhere.** Extend the existing pattern to the six builders that lack it, and to `app.py`'s `get_data` path so the dashboard, plant view, machine view and overview all surface it. Use the same sentinel; do not invent a second mechanism.

**(c) Never cache a partial.** A result assembled from any failed or partial read must not be written to cache, so the next request retries.

### Validate

- Force a partial read: the affected plant shows a warning, not a smaller total.
- Force a genuinely idle month: renders as zero **without** a warning. The two must be distinguishable.
- Partial results are not cached; the next request retries.
- **No figure moves on a complete read:** Pipe 1,283,300.15 / 6,507 h · Moulding 366,015.39 / 35,972 h · PTMT 524,467.607 net / 557,264.061 gross · Garden 262,818.23 · HDPE 23,817.24 · Tank litres and both rejection bases. If any moves, **stop**.
- Add a fixture: a loader returning a partial population produces a flagged result, never a clean total.

## Why this matters beyond the symptom

The acceptance fixtures committed in `b09a165` pin five figures **offline with mocked loaders**, so they pass regardless of what a live read returns. They verify the arithmetic, not that the arithmetic saw every row. Until a partial read is detectable, a live figure cannot be trusted just because its fixture passes.

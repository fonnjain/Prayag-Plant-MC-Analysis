# Garden Rejection — Join It From the Daily Report Matrix

Read `PRAYAG_RULES.md` first. Touches **R-04, R-06, R-08, R-09, R-23, R-35**.

## The defect

QA reports, across four months: *"REJECTION IS IN SHEET IN DAILY REPORT WORKING SHEET BUT NOT IN DASHBOARD"*, and for July specifically *"REJECTION DATA IS IN SHEET MACHINE 3 BUT NOT IN DASHBOARD"*. **They are right.**

Garden output comes from the `MACHINE 1-4` block tabs, which genuinely have **no rejection column** (verified header band: `DATE | CODE | SIZE | LENGTH | NOS | TOTAL | KG | TOTAL | RP CONSUMPTION | Remarks`). That is why Phase 1 gated Garden rejection to `n/a` — correct reasoning, wrong premise.

**Rejection IS in the daily source** — in the `Daily Report` matrix, the same tab the app already opens for run hours. `parse_daily_matrix` explicitly reads *"the raw triplet (run hours, output, rejection)"*. The Garden join in `sheets.py` (~line 1776–1792) then discards everything except hours:

```python
for rr in rh_rows:
    if rr.actual_hours and rr.actual_hours > 0:      # ← guard
        rh_map[(machine, date)] = ... + rr.actual_hours
for r in raw:
    if key in rh_map:
        r.actual_hours = rh_map[key]                 # ← hours only
```

Rejection is parsed, then thrown away.

---

## TWO TRAPS — a naive fix fails on both

**Trap 1 — the hours guard would skip July entirely.**
July's Garden `Daily Report` has **0 run hours** but **1,853.50 kg of rejection** (MACHINE-2 = 70.00, MACHINE-3 = 1,783.50). A rejection map built inside `if rr.actual_hours > 0` misses exactly the month QA complained about. **Build the rejection join independently of the hours guard.**

**Trap 2 — the denominator belongs to a different output basis.**
Output on screen comes from the block tabs (July **68,390 kg**). The rejection comes from the `Daily Report`, whose own output for July is **32,191 kg**. Pairing them naively gives 1,853.50 ÷ 68,390 = **2.71%** — wrong. The sheet's own answer is **5.76%**.

Use the existing mechanism: `Record.reject_denominator` (added for the Tank fix; `compute_metrics` already sums it as `_reject_denom_sum`). Join the `Daily Report`'s **own output** for that machine-date as the denominator, giving 1,853.50 ÷ 32,191 = **5.76%** — matching the sheet and the annual.

---

## Required change (Garden path only)

In the Garden run-hours join:

1. Build a **rejection map** from the same `rh_rows`, keyed `(machine number, date)` — **not** gated on `actual_hours > 0`.
2. Build an **output map** from the same rows (the `Daily Report`'s own output kg per machine-date).
3. On each block-tab record where the key matches: set `reject_count` from the rejection map, `reject_denominator` from the output map, and `rejection_tracked = True`.
4. Where the matrix supplied **no** rejection value for a machine-date, leave `rejection_tracked` as it is (`False` from `parse_daily_blocks`) so the no-fake-0% invariant still suppresses rather than showing a false zero (**R-08**).
5. Do **not** change output. Output stays from the block tabs. Do not sum, average, or reconcile the two bases (**R-23** is still open).

### Basis divergence must be visible (R-23, R-35)

Displayed output (block tabs, 232,528 kg Apr–Jul) and the rejection denominator (`Daily Report`, 138,052 kg) are different bases. A user seeing "output 232,528, rejection 3.81%" could reasonably multiply them and get the wrong kg.

Where the two bases differ by more than **2%** for a month, surface a note in the existing warning/data-health mechanism naming both figures — e.g. *"Garden rejection % is measured against the Daily Report output basis (32,191 kg), which differs from the displayed block-tab output (68,390 kg)."* Do not silently reconcile them.
